# ADR-0001: gwi Is Standalone: Forked Infrastructure, Own Config, Log and MCP Server

## Status

🟡 Proposed (2026-10-07,
[rust-works/omni-dev#2203](https://github.com/rust-works/omni-dev/issues/2203)). The
matching decision on the omni-dev side is
[omni-dev ADR-0095](https://github.com/rust-works/omni-dev/blob/main/docs/adrs/adr-0095.md);
the inventory and phases are in
[omni-dev's plan](https://github.com/rust-works/omni-dev/blob/main/docs/plan/gwi-extraction.md).

## Context

gwi (Google Workspace Interface) takes over omni-dev's `gmail` and `drive` command trees,
their 23 MCP tools and the ADRs behind them, about 195k lines in all. That code leans on
omni-dev infrastructure: secret and secret-file handling (STYLE-0030, omni-dev ADR-0089 and
ADR-0090), the environment-injection seam, the settings loader, the request log and its
fail-closed `audit.jsonl` sink, the file-lock and `0600` helpers, and a large test-support
harness. omni-dev's settings file and request log in turn carry Google-specific types.

The shared modules are self-contained, so three arrangements were possible. gwi could depend
on omni-dev as a library, which drags `ratatui`, `alacritty_terminal`, `axum`, `git2` and
`syn` into a Gmail/Drive CLI, makes omni-dev's library surface a public contract and forbids
omni-dev ever depending on gwi. A shared core crate avoids that but needs a refactor of
about 12k lines and a second release train to serve two consumers. Forking copies only what
gwi needs and lets each project evolve its settings schema, log and release process alone.
Users have an existing `~/.omni-dev/settings.json`, Drive lease ledger and request log, and
a choice had to be made between reading them in place and owning new locations.

## Decision

We will make gwi a standalone project that shares no crate with omni-dev.

1. **Fork the infrastructure.** We copy the needed modules from omni-dev once, at a commit
   recorded in the omni-dev plan, and own them from then on. The rules that govern them
   (STYLE-0028 env injection, STYLE-0030 secrets, the grep-guard tests) come with them and
   are not weakened.
2. **Own configuration and state.** gwi reads `~/.gwi/settings.json` and keeps its ledgers
   under `<state_dir>/gwi/`. A `gwi` import command copies the `gmail`, `drive` and `lease`
   settings blocks and the Drive lease ledger from omni-dev's locations. It copies and never
   moves, is idempotent, refuses to overwrite existing gwi state without `--force`, and takes
   the ledger lock while copying. Gmail insert and sync state lives with each archive
   directory and needs no migration.
3. **Own log and audit sink.** gwi writes its own `log.jsonl` and fail-closed `audit.jsonl`.
   Records written by omni-dev are not copied, so they keep their provenance, and neither
   file's guarantees (exempt from the disable switch, rotation and pruning for `audit.jsonl`)
   are weakened to ease the move. The record schema carries a version field.
4. **Own MCP server.** The Gmail and Drive tools are served by `gwi-mcp`, built behind an
   `mcp` feature like omni-dev's `omni-dev-mcp`.
5. **Names.** The crate is `gwi`, the binaries are `gwi` and `gwi-mcp`. Environment variables
   read by the moved code take a `GWI_` prefix in place of `OMNI_DEV_`, with no fallback; the
   unprefixed `GMAIL_*` and `DRIVE_*` credential names keep their spelling.
6. **History.** The moved paths keep their history through `git filter-repo`, at the same
   relative paths so blame survives, with bare `#N` references rewritten to
   `rust-works/omni-dev#N`.
7. **Live testing.** Live tests against real Google accounts stay manual and local. CI runs
   the mock-server tests only and never holds Google credentials. Account names and test
   folder ids are not recorded in this repository.

## Consequences

- gwi builds fast and light, has no dependency on omni-dev's release cycle, and is free to
  change its settings schema, log and MCP surface.
- The forked modules can drift from omni-dev's copies. A security fix to secret handling or
  the audit sink in either project is not automatic in the other, so a fix to a module
  copied from the fork-point must open a matching issue in the other project.
- Users move once: install gwi, run the import, and for MCP add `gwi-mcp` as a second server.
  Scripts that set `OMNI_DEV_*` variables for Gmail or Drive must be updated.
- Audit history is split across two files: records before the move stay in omni-dev's
  `audit.jsonl`, and gwi's start fresh. A reader who wants the full history reads both.
- The import command is new, security-relevant code (it reads credential references and
  copies a lock-protected ledger) and needs its own tests against a real omni-dev settings
  file and ledger before the first release.
- The crate name `gwi` is not reserved on crates.io until the 0.0.1 placeholder is
  published, and `gwi` is already taken on npm, which matters only if gwi ships there.
